Mamba, GDN and attention hybrids · clarified 27 October 2026

Where Mamba and hybrid models can resume a cached prefix

Full attention retains keys and values for earlier tokens. A recurrent layer, such as Mamba or Gated DeltaNet (GDN), updates a fixed-size state as it reads them. Reusing a prefix requires a saved state at the resume point. That rule applies to both pure Mamba and attention hybrids; the large block sizes calculated below come from vLLM's hybrid memory allocation.

The short version. Pure Mamba needs a complete recurrent-state checkpoint. A Mamba–attention hybrid also needs the attention KV through that same token. In the vLLM hybrid allocation modeled here, fitting both kinds of state into equal-sized pages sets a token block size N. The scheduler decides which boundaries actually get checkpoints, and LMCache's final offload chunks must align with the engine's cache groups. Pure Mamba has no attention pages to match, so this hybrid formula does not determine its checkpoint spacing.

Mamba and GDN are different model architectures. Mamba uses a selective state-space model (SSM); Qwen3.5 uses Gated DeltaNet linear attention. vLLM's mamba cache names cover several recurrent backends. A shared flag or storage interface does not make their state tensors, kernels or numerical behavior interchangeable. Mamba-1 and Mamba-2 also have different state layouts; use the engine's complete state specification.

One pure-Mamba snapshot stays the same size as the prefix grows. A snapshot after 32,000 tokens has the same tensor dimensions as one after 2,000 tokens for the same model and runtime. Keeping many possible resume points still requires many snapshots. A hybrid additionally retains attention KV that grows with prefix length. This changes restore traffic: pure Mamba needs one complete model-state snapshot, while a hybrid also needs the attention history that is not already resident.

The checkpoint principle applies to all three rows. The model selector, page-size estimates and scheduler figures below cover attention hybrids only. They do not establish a minimum checkpoint interval for pure Mamba or prove LMCache support for a particular model. See what support means and the implementation sources .

Why these hybrids have large checkpoint blocks

In the hybrid allocation scheme modeled here, vLLM uses equal-sized pages for attention and recurrent layers. Pure Mamba has no attention pages to reconcile.

N follows the size of the live state in GPU memory. Storing a checkpoint in a smaller format on CPU or disk does not change it; the storage section shows why.

Which boundaries actually get a checkpoint

This figure models the base case where the kernel exports state at the end of a scheduler step. vLLM's align mode cuts prefill steps so that they end on block boundaries.

The rule comes from vLLM's scheduler. A prefill step that stops short of the prompt end is rounded down to a whole number of blocks, and no step runs past the prompt's last block boundary. The prompt's final partial block is left without a checkpoint. With a budget between N and 2N−1, every step covers exactly one block, so every boundary gets a checkpoint. A larger budget can reduce prefill steps, but a step may then cover several blocks and only its last boundary is saved. A budget of 2N−1 is an optional way to retain every ordinary boundary in this example while leaving room for decoding requests. Current LMCache also accepts larger budgets; dense checkpoint placement is a tuning choice, not a requirement for correct offload. Its align-mode connector requires a budget of at least N.

align is vLLM's default when prefix caching is on. The older all mode saves every boundary regardless of steps, but it is deprecated at the pinned commit and GDN backends do not support it. An internal scan chunk used by a Mamba or GDN kernel is a separate quantity from N; its size and restrictions depend on the backend.

This figure models one request running alone, with no speculative decoding. The pinned scheduler can add three more stopping points that are left out here: the prompt's last hash boundary when a finer prefix-match unit is configured, the point where a request was seen to diverge from an earlier one, and a checkpoint that some backends export from inside the final step.

vLLM sets N; LMCache offload chunks follow it

LMCache's current multiprocess connector negotiates a final chunk size from the engine's resolved cache groups. The alignment remains; how you configure it has changed since the September recipe.

In the current connector, --chunk-size is a minimum. The connector finds the least common multiple of the cacheable groups' effective token spans and rounds the configured minimum up to a multiple of it. For the simple hybrid setup here, that alignment is N, so the final size is C = k × N . The default minimum of 256 can therefore resolve to a much larger final chunk.

With the Qwen3.5-4B FP32 recurrent-state scenario, BF16 attention KV and 16-token vLLM alignment, this page estimates N = 528. If the engine reports that value, a configured minimum of 256 resolves to 528; a minimum of 768 resolves to 1056. A final size of 768 would still be incompatible with N = 528. Selecting 256-token vLLM allocation alignment instead estimates N = 768; that control changes the engine-sizing assumption, not LMCache's configured minimum.

Version boundary: the September snapshot required an explicitly compatible chunk size and rejected mismatches. With that older connector, set N or a multiple of N yourself. With the newer connector, verify the negotiated size. Once an MP server's final size is fixed, another client must be compatible with it; negotiation does not resize an active server for a different model.

What LMCache support does—and does not—establish

                    

                        

                            The engine creates a checkpoint; LMCache stores and restores it.
                            The multiprocess integration transfers recurrent states as opaque pages, using the engine's
                            layout. Its hybrid recipe requires
                            --separate-object-groups
                            so recurrent and full-attention layers have separate cache objects. A cache hit is usable
                            only when all required groups are available at a consistent resume point. Restoring
                            attention KV alone does not let a hybrid skip its recurrent prefix computation.
                        

                        

                            Pure-Mamba engine support is not an end-to-end LMCache test.
                            At the October vLLM source revision linked below, both the Mamba-1 and Mamba-2 model classes
                            declare prefix-cache support. The LMCache recipes reviewed here validate selected GDN and
                            Kimi linear-attention hybrids; they do not provide a pure-Mamba restore recipe or validate
                            every Mamba hybrid in this calculator. That is an evidence gap, not a finding that those
                            models cannot work. The sample commands for them are configuration projections.
                        

                        

                            Verify a real external restore for the exact model and runtime.
                            Clear or evict the engine's local prefix cache while preserving the external cache, then
                            confirm that recurrent state and convolution history are loaded and used. For hybrids, check
                            the matching attention KV too. Compare a fresh run with a restored run, including changed
                            suffixes, missing components and repeated reuse. Use a numerical or quality check
                            appropriate to the backend; GDN's documented validation compares task scores because cached
                            and fresh runs need not produce bit-identical output.
                        

                    

                    

                        Shared cache infrastructure does not make checkpoints portable across models, state layouts,
                        precisions or engine backends. The opaque-page hybrid path does not by itself provide CacheBlend
                        or CacheGen support. The compressed sizes below remain projections, not tested Mamba codecs.

What this calculation assumes

                    
The simplified aligned-page model for attention hybrids is:

                    
S = recurrent matrix values × working bytes + convolution values × 2
T = KV values per attention layer per token × 2
N = A × ceil(S / (A × T))
P = N × T

                    

                        S
                        is the live recurrent payload,
                        T
                        is attention bytes per token,
                        A
                        is the assumed effective allocation alignment,
                        N
                        is the block size, and
                        P
                        is the shared page. The selected
                        A
                        stands in for backend constraints and a requested block size; it is not inferred from a GPU.
                        Additional groups, MLA layouts, quantized KV, tensor parallelism, speculative scratch state and
                        extra auxiliary state can change this calculation. Pure Mamba has no attention bytes per token
                        T: this formula is inapplicable, not a reason to assign it an infinite or zero checkpoint
                        interval.
                    

                    

                        Model configuration describes dimensions; the engine resolves state dtype and layout. FP32 is an
                        explicit scenario here, not a default attributed to all four models. The Qwen config requests
                        FP32 SSM state, while the other linked configs do not establish that same request. Inspect
                        actual cache specs and startup logs before quoting a deployment number.
                    

                    

                        One live state per conversation and many retained prefix checkpoints have different memory
                        costs. If every attention block has one recurrent checkpoint and per-layer pages are equal, the
                        recurrent share is the recurrent branch count divided by the total branch count. Sparse
                        checkpoints, shared prefixes, padding and eviction change that share. Count unique retained
                        objects, and report GPU allocation, serialized bytes and transferred bytes separately.
                    

                    

                        For a real deployment, verify checkpoint positions and actual restores after GPU eviction;
                        require complete attention, recurrent and convolution state at the same boundary. Test changed
                        suffixes, exact block boundaries and missing components. Storage compression also needs quality
                        measurements at its actual store/restore cadence, including chained reuse.
